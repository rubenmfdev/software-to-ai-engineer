## Done
- Built a job-posting extractor in [llm-assistant](https://github.com/rubenmfdev/llm-assistant): a pydantic schema (`title`, `company`, `location`) and a reply that is validated before it is trusted
- Handled bad output on purpose: wrong type, missing field, empty reply, and several jobs in one text each raise their own error and keep the raw reply
- Added one retry that sends the validation error back to the model, and only for malformed output
- Added a grounding check: every extracted value must appear in the source text
- Treated the posting as untrusted data: it goes between `<posting>` tags and tag lookalikes are stripped
- 32 unit tests with a fake model, no real model needed
- An eval script with 12 cases (clean, messy, German, Spanish, no location, two jobs, not a posting, four prompt-injection variants). It passes 12 of 12 against `devstral-small-2:24b`, in about 38 s
- Rewrote the README with the setup and the design decisions

## Learned
- Valid JSON is not the same as JSON that matches my schema. `json_object` only promises the first, so the schema is enforced by my prompt and my parser
- A deterministic model can still be wrong. Validation checks the shape, not the truth
- A missing value should be `None`, not `""`, so "the posting has no location" is different from "the model failed"
- Unit tests and evals are different things. Tests are fast and use a fake model, evals call the real one and can vary
- A grounding check proves a value came from the input, not that it is correct or safe. The "Head of Finance at Evil Corp" posting passes every check I have: it is valid JSON, the values are in the source, and nothing looks wrong. Right now it is harmless because I only print the result. If the values triggered an action, I would need a human review or a trusted source to check them against
- Strict schema mode (`json_schema`) guarantees the **structure** of the reply, not its content. When I asked the model something unrelated, it ignored the request and invented five fake job postings to fill my schema. My grounding check would reject all of them

## Experiment: `json_object` vs strict `json_schema`
Ran my 12 eval cases three times in each mode against `devstral-small-2:24b` (comparison script run with Claude's help, not kept in the repo).

| Mode | Pass | Retries | Time |
|---|---|---|---|
| `json_object` | 12/12, 3 of 3 runs | 0 | 29-37 s |
| `json_schema` | 12/12, 3 of 3 runs | 0 | 29 s |

No difference on these cases, so I keep `json_object`. The stricter mode would matter for a weaker model, or one that often breaks the schema. Not every model or provider supports it.
