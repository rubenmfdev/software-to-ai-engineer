## Learned
- FastAPI validates the input with pydantic before the endpoint runs, so my function only sees data that already matches the model. The same idea as Phase 1: input is untrusted until it is validated
- The API key check lives in a dependency, not inside each endpoint. One place, and it runs before the body is processed
- `async def` endpoints all run on one event loop in one thread. `await` is the point where an endpoint gives control back so another request can run. A blocking call inside `async def` (a sync HTTP client, `time.sleep`, a sync model client) freezes the whole server. A plain `def` endpoint runs in a thread pool, so blocking is fine there
- The model is an untrusted caller of my tools. The guarantees must come from code (path guard, validated arguments, which tools exist), not from asking the model to behave. The path guard stops leaving `postings/`, but anyone with the key can still read every file inside it, so with several users I would need a folder per client
- Async is not the same as threads. Swift's `async/await` runs on a pool of threads that the system manages, and a task can resume on another one. Python's `async def` gives concurrency on one thread, and only while the code waits. CPU work or blocking calls never overlap

## Broke / confused me
- `main.py` had a stray `∫` at the end of the file, a syntax error, so nothing ran
- The 404 message lacked the `f` prefix and showed `{item_id}` literally
- `text: str = None` has the wrong type: it must be `str | None`
- I did not know why `async def` does not use several threads like Swift. Python's asyncio runs on one thread and only switches at an `await`, because the GIL means threads would not run Python in parallel anyway (see Learned)
- In review: a non-ASCII API key gave a 500 (`compare_digest` needs bytes), an error from the model server (wrong model, 429) gave a 500, and the model call had no timeout, so a hung server would hold a request for 10 minutes. All three have a test now
