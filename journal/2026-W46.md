## Learned
- The model never runs a function. I send the tool schemas with the request. If the model thinks a tool is useful, the reply contains a tool call instead of an answer. My code runs the function, sends the result back (linked to the call by its id, together with the whole history, because the model has no memory), and asks again
- The loop ends when a reply has no tool calls. The model decides when it is done
- The limit of 5 rounds is not a retry. It is a safety cap: a confused model could call tools forever and burn time and tokens. My code stops and raises an error
- The tool call comes from the model, so it is untrusted input. I validate the name and the arguments, and extra arguments are an error, so the model cannot pass something I did not declare
- A tool error goes back to the model as the tool result, so it can fix its own call (for example a wrong filename) instead of the whole program crashing
- The filename comes from the model, so `read_posting` must stay inside its folder. In one live test the model refused a path escape by itself, but my code does not depend on that: the guard is in the code and has its own tests
- Tool output is untrusted too. The file contents and the extracted fields are wrapped in tags and marked as data, the same as the posting in Phase 1

## Broke / confused me
- The grounding check compares the extracted values with the text the model passed to `extract_posting`, not with the file. If the model changed the text between the two calls, the check would still pass
- The prompt says `postings/acme.txt` but the tool wants only `acme.txt`. It worked with this model, but a weaker one could get a "not found" error first
